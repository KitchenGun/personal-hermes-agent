# 클라우드 개발과 VM 배포 인계

이 문서는 클라우드에서 변경을 준비하고 VM에서 승인된 변경만 반영할 때의
인계 기준입니다. VM은 운영 상태의 단일 source of truth로 유지합니다.

## 검증 상태와 적용 범위

2026-10-02 기준 설치된 `verify-commit-v1` 프로필은 Hermes 저장소의
`dff2a411144b073b4af363ec0bf959d9bb028bad`가 `main`에 있는지 확인하고
`verified` 결과를 반환했습니다. 해당 결과는 production deployment를 수행하지
않았다고 명시합니다. 이 검증은 새 문서 패치의 SHA 검증이나 런타임 배포 성공을
의미하지 않습니다.

아래 문서 전용 staging과 운영 배포 프로필은 추가 구현·검토가 필요한 기준입니다.
`verify-commit-v1`의 설치·동작 확인을 이 프로필들의 구현·설치·검증 완료로
대체하지 않습니다. 설치된 검증 기능과 제안된 배포 절차를 구분해서 사용합니다.

## 역할과 경계

- 클라우드: 공개 저장소의 코드·문서 수정, 변경 범위에 맞는 검증, GitHub 커밋 게시
- GitHub: 검토 가능한 diff와 변경 불가능한 전체 커밋 SHA를 통한 인계
- VM: 허용된 저장소와 고정 배포 프로필을 확인한 뒤 승인된 SHA만 반영
- 로컬 PC/WSL: 기존 터널과 비활성 백업/캐시 역할 유지; 코딩과 검증은 클라우드에서 수행

운영 secret, 채워진 env, raw log/DB, 개인 데이터와 private workspace path는
클라우드나 GitHub로 옮기지 않습니다. VM 프로필의 실제 경로와 인증 정보도
이 공개 문서에 기록하지 않습니다.

## 1. 클라우드에서 변경 준비

1. 시작 HEAD와 `git status --short`, `git diff --stat`를 확인합니다.
2. `AGENTS.md`와 변경 대상의 지침을 읽고 unrelated dirty change를 보존합니다.
3. 작은 변경 단위와 검증 범위를 정합니다. 자원이 제한된 환경에서 전체 테스트를
   무조건 실행하지 않고, 변경에 필요한 focused test와 정적 검사를 먼저 정합니다.
4. 실행한 명령, 종료 상태, 미실행 항목과 실행 환경 차이를 기록합니다.
5. 공개 안전 검사를 수행한 뒤 승인된 브랜치에 게시하고 GitHub의 전체 SHA를 확인합니다.
   기본 브랜치 직접 push는 명시적 승인이 있을 때만 수행합니다.

문서만 변경했을 때의 공개 전 기본 검증:

```bash
git diff --check
bash scripts/examples/scan-for-secrets.sh
bash scripts/examples/validate-examples.sh
```

`validate-examples.sh`는 job registry 검증도 실행하며 Python의 PyYAML이 필요합니다.
이 검사는 문서·예시의 제한된 정적 검증입니다. dashboard 런타임, 인증, 실제 배포의
정상 동작을 보증하지 않습니다. 변경한 Markdown 링크도 대상 파일이 있는지 확인합니다.

Node 버전이 클라우드와 VM에서 다르면 검증 결과에 두 환경을 구분해서 적습니다.
예를 들어 Node 24에서 통과한 테스트만으로 Node 22 호환성을 확정하지 않습니다.

## 2. SHA 기반 인계

인계에는 다음 정보를 포함합니다.

- 허용된 GitHub 저장소와 검토용 브랜치/커밋 링크
- 기준 전체 SHA와 배포 대상 전체 SHA
- 변경 파일 목록, 목적, 문서 전용인지 런타임 변경인지
- 실행한 검증 명령과 결과, 미실행 항목 및 환경 차이
- 승인된 VM 고정 프로필 식별자와 예상 영향
- 배포 후 확인 기준 및 런타임 변경 시 rollback 기준

브랜치명만으로 배포 대상을 정하지 않습니다. 인계 후 브랜치가 이동해도 대상 SHA는
바뀌지 않습니다. 인계 내용에 임의 shell 명령, 서비스명, 파일 경로를 넣어 VM의
고정 프로필을 확장하지 않습니다. 프로필 변경은 별도로 검토하고 승인합니다.

## 3. VM 사전 검사와 반영

VM 배포는 사전에 승인된 고정 프로필의 허용 범위 안에서만 수행합니다.
프로필은 저장소, 배포 대상 경로, 허용 파일, 필요한 검증과 재시작 서비스를 제한해야
합니다. 아래 항목을 확인할 수 없으면 배포를 멈추고 원인을 보고합니다.

1. 저장소가 allowlist에 있고 전달받은 전체 SHA를 해당 저장소에서 확인할 수 있습니다.
2. 기준 SHA와 대상 SHA 사이의 실제 diff가 인계된 범위 및 프로필 허용 파일과 일치합니다.
3. VM의 현재 HEAD와 dirty change를 확인했습니다. 기존 변경을 덮어쓰거나 자동으로
   stash/reset/clean하지 않습니다. 예상 기준과 다르면 새 기준으로 재검토합니다.
4. env와 운영 상태는 VM-local로 유지하고, 기존 권한과 보안 경계를 보존합니다.
5. 런타임 변경이면 반영 전 복구 가능한 백업과 rollback 절차를 확보했습니다.

문서 전용 변경은 소스 반영과 SHA 확인만으로 끝내며, 서비스 재시작이나 런타임 파일
복사를 하지 않습니다. 런타임 변경은 프로필에 정의된 파일만 반영하고 필요한 서비스만
재시작한 뒤 해당 smoke test를 수행합니다. dashboard 검증은 [운영 안내](../ops/README.md)의
smoke test와 [dashboard 문서](12-codex-control-dashboard.md)를 따릅니다.

검증 실패 시 성공으로 보고하지 않습니다. 승인된 rollback 범위 안에서 복구하고,
복구한 버전과 재검증 결과를 남깁니다. 복구에 추가 권한이 필요하면 중단하고 요청합니다.

문서 artifact를 별도 staging에 내려받아 SHA와 허용 파일을 검증하는 단계는
운영 소스 반영과도 구분합니다. staging 검증 성공은 런타임 배포 성공이 아닙니다.

## 4. 완료 보고

GitHub 게시, 문서 artifact/staging 검증, VM 소스 반영, 런타임 배포, smoke test는
각각 구분해서 보고합니다.
완료 보고에는 확인한 GitHub SHA, VM 반영 SHA, 실행한 검사 결과, 재시작 여부,
남은 제약을 포함합니다. 한 단계의 성공을 다음 단계의 성공으로 대신하지 않습니다.
